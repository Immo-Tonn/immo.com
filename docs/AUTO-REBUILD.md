# Автопересборка сайта после изменения объектов

Статический сайт (prerender) показывает объекты, которые были в API **на момент сборки**.
Чтобы новые, изменённые и удалённые объекты появлялись сами, backend после успешного
сохранения запускает пересборку frontend через Vercel Deploy Hook.

> **Статус: код написан и проверен на mock-сервере; весь путь целиком НЕ проверен.**
> Реальный Deploy Hook не создавался и не вызывался. Не проверено: настоящий хук Vercel →
> сборка → новый объект на сайте. Автоматическое обновление нельзя считать готовым, пока не
> пройдена проверка из раздела «Как проверить целиком».

## Как это работает

1. Админ создаёт/меняет/удаляет объект → `POST/PUT/DELETE /api/objects[/:id]`
   (`BE/src/controllers/realEstateObjectsController.ts`).
2. **После** успешного сохранения и отправки ответа клиенту контроллер вызывает
   `requestFrontendRebuild('object:create|update|delete')` (`BE/src/utils/rebuildHook.ts`).
   При ошибке сохранения (400/404/500) вызова нет.
3. Изменения за короткое время сливаются в один запуск: хук вызывается через
   `REBUILD_DEBOUNCE_MS` (по умолчанию 30 с) после **последнего** изменения, но не позже
   `REBUILD_MAX_WAIT_MS` (5 мин) после первого. Сценарий «создание → загрузка фото →
   финальное обновление» даёт один запуск уже с готовыми данными.
4. `POST` на адрес хука; при сбое — ещё 2 попытки (через 2 и 10 с), таймаут запроса 10 с.
5. Ни один сбой не отменяет сохранение объекта и не меняет ответ API: вызов идёт после
   ответа, не ждётся и не бросает исключений. Итог пишется в лог (`[rebuild] …`) —
   без адреса хука (в лог попадает только статус/код ошибки).
6. Vercel собирает сайт: `react-router.config.ts` читает объекты из API, prerender строит
   HTML, `scripts/postbuild.mjs` пишет `sitemap.xml` и `built-objects.json` из того же
   списка. Если API при сборке недоступен — сборка падает, прежняя версия остаётся.

## Что пользователь видит между сохранением и готовой сборкой (минуты)

| Событие | До окончания пересборки |
|---|---|
| Новый объект | в списке его нет, URL отвечает HTTP 404 и показывает страницу 404 |
| Изменённый объект | в HTML прежние данные; после загрузки страницы данные тихо обновляются из API |
| Удалённый объект | URL ещё отдаёт старый HTML (200), после загрузки показывается «Objekt gelöscht»; из списка исчезает сразу |
| sitemap | прежний |

После успешной сборки всё приведено в соответствие. Если запуск или сама сборка не удались,
сайт останется на прежней версии до следующего успешного запуска.

## Что нужно сделать для подключения (я этого не делал)

1. В Vercel: проект → Settings → Git → Deploy Hooks → создать хук (имя, например
   `objects-changed`), выбрать **ветку, которая публикуется** (сейчас это `dev`; хук на
   `dev` запускает Production-деплой). Лимиты: до 5 хуков на проект, до 60 запусков в час.
2. **Проверка до слияния:** создать отдельный хук на ветку `feat/seo-prerender-prototype` —
   он запускает только Preview-деплой и не затрагивает production.
3. Адрес хука — секрет. Хранить только в окружении backend-сервера (Hetzner,
   docker-compose) как `FRONTEND_DEPLOY_HOOK_URL`; не коммитить и не вставлять в чаты и
   логи. Для текущего окружения: добавить переменную в окружение контейнера `my-backend`
   и перезапустить его (`docker-compose up -d --build`; вручную на сервере).
4. Необязательно: `REBUILD_DEBOUNCE_MS`, `REBUILD_MAX_WAIT_MS` (миллисекунды).
5. Без переменной механизм отключён (в лог пишется предупреждение). Это же способ быстро
   выключить автопересборку.

## Как проверить целиком (после подключения хука на ветку прототипа)

1. Создать **тестовый** объект в админке (или изменить существующий) при заданном хуке.
2. В логе backend: `[rebuild] пересборка frontend запущена`; в Vercel — новый Preview-деплой.
3. После сборки на Preview: объект есть в списке, URL объекта отдаёт 200 с полным HTML,
   объект в `sitemap.xml` и `built-objects.json`.
4. Удалить тестовый объект → после следующей сборки URL отдаёт 404, из sitemap исчез.
5. Проверить, что при недоступном хуке (неверный адрес) сохранение объекта проходит, а в
   логе есть сообщение об ошибке.

## Ограничения

- Отложенный запуск хранится в памяти процесса: при перезапуске backend в течение паузы
  (≤ 30 с) запуск теряется. Страховка не реализована (например, периодический запуск
  хука по расписанию).
- Хук вызывается только из контроллера объектов (создание/изменение/удаление объекта).
  Отдельные эндпоинты загрузки/удаления фото и видео его не вызывают; в текущем сценарии
  админки объект сохраняется (`PUT`) после загрузки медиа, и этот вызов запускает
  пересборку. Иные пути изменения медиа не покрыты.
- Лимит Vercel (60 запусков в час) при частых правках; серия правок сливается в один запуск.
- Автотест: `cd BE && npm run test:rebuild` (11 проверок на mock-сервере: успех, слияние,
  повторы, ограничение числа попыток, недоступный сервер, нет переменной/неверный адрес,
  отсутствие секрета в логах, вызов после успеха и ответ API при сбое хука).
