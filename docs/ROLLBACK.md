# Восстановление стабильной версии (перед SEO-миграцией)

Перед началом работ по SEO/prerender/языковым URL сохранено рабочее состояние проекта.
Документ описывает, как его открыть и как вернуть на production. Описаны только
действия, проверенные при подготовке (см. раздел «Что не проверено»).

## Как публикуется сайт (фактически)

- **Frontend (immo-tonn.com)** — Vercel, подключён к GitHub. Любой push в `dev`
  создаёт Production-деплой. Push в другие ветки создаёт только Preview-деплой.
- **Backend / API (immo-tonn.de)** — Docker Compose на сервере Hetzner, вручную
  (см. раздел «Деплой» в README). Откат frontend backend не затрагивает.
- GitHub Actions (`.github/workflows/deploy-*.yml`) срабатывают только на ветку `main`
  и папки `frontend/`/`backend/`; в репозитории их нет, так что не запускаются.

> ⚠️ **Merge в `dev` может автоматически опубликовать сайт на production.**
> Резервная ветка и тег на GitHub не запускают production-деплой (проверено: после их
> отправки новых Production-деплойментов не появилось).

## Открыть старую версию локально, не потеряв текущую работу

Отдельная рабочая папка рядом с проектом; ваши ветки и незакоммиченные изменения
не затрагиваются:

```bash
git fetch origin --tags
git worktree add --detach ../immo_com-stable stable-before-seo-migration-2026-10-29
cd ../immo_com-stable/FE
```

Зависимости (одинаковые с `dev` на момент сохранения): проверенный вариант — ссылка
на `node_modules` основного проекта (`ln -s <путь>/FE/node_modules node_modules`), затем `npx vite --port 5391`
(порт любой свободный; не занимайте порты чужих процессов).

Убрать папку после просмотра: `git worktree remove ../immo_com-stable`.

Простое переключение ветки (`git checkout`/`git switch`) **публичный сайт не меняет**:
production обновляется только после push в `dev`.

## Откат production

Backend не затрагивается — откатывается только frontend.

Рекомендуемый способ — новый коммит, возвращающий дерево файлов к сохранённому, история
не переписывается:

```bash
git fetch origin --tags
git switch -c restore/stable-2026-10-29 origin/dev
git read-tree -u --reset stable-before-seo-migration-2026-10-29
git diff --cached --stat stable-before-seo-migration-2026-10-29   # должно быть пусто
git commit -m "Откат к stable-before-seo-migration-2026-10-29"
git push -u origin restore/stable-2026-10-29
```

Затем открыть PR в `dev`, проверить Preview-деплой этой ветки, и **только после
проверки** смёржить: merge в `dev` опубликует старую версию на production.
`read-tree -u --reset` возвращает и удалённые, и убирает добавленные после тега
файлы (процедура проверена на копии репозитория).

Нельзя: `git push --force` в `dev` и переписывание истории `dev`.

## Что вернёт откат

- **Полный откат** (команды выше) возвращает всё состояние сохранённой версии, включая
  старую архитектуру (клиентский рендеринг без prerender, одноязычные URL) и прежнюю
  SEO-разметку.
- **Только старый дизайн** (без отката архитектуры/SEO) — отдельное изменение: нужно
  откатывать конкретные коммиты дизайна (`git revert <sha>`), а не восстанавливать
  дерево из тега.
- Изменения backend (вызов Deploy Hook при изменении объектов, см. [AUTO-REBUILD.md](AUTO-REBUILD.md))
  откатываются отдельно, вручную на сервере. Быстро отключить автопересборку можно, убрав
  переменную `FRONTEND_DEPLOY_HOOK_URL`: без неё хук не вызывается.

## Что не проверено

- Откат через интерфейс Vercel (переключение на предыдущий деплой) — доступа к
  панели Vercel не было; перед использованием сверьтесь с её документацией.
- Настройка «Production Branch» в проекте Vercel: что это `dev`, установлено по истории
  деплоев GitHub, а не по панели.
